# OpenRice 用户系统开发框架

> **定位：** 本文是 OpenRice 用户系统、Web 多租户、角色权限和团队空间的权威开发框架。后续涉及账号、组织、工作区、数据归属、SkillHub、数字员工、连接器、Memory 或资源库权限的设计与开发，必须先阅读并遵循本文。
>
> **相关 Issue：** [MET-33 OpenRice 用户系统：Web 多租户、角色权限与团队空间](https://linear.app/metasnowsky/issue/MET-33/openrice-用户系统web-多租户角色权限与团队空间)
>
> **最近核对：** 2026-08-03 EDT

## 一、产品定位

OpenRice 当前以桌面端、本地优先和单人使用为主。网页版虽然可以访问，但没有完整的用户身份、组织空间、角色权限和数据隔离，不能直接作为多人协作产品投入使用。

用户系统不是一个独立登录页，而是 OpenRice Web 化的统一治理底座：

```text
身份认证
  + 组织 / 工作区 / 成员
  + 角色与权限
  + 资源归属与数据范围
  + 凭证与连接器隔离
  + 审计与安全策略
              ↓
对话 / 任务 / SkillHub / 数字员工 / Memory / 资源库 / 文件 / Loop
```

桌面本地模式与 Web 团队模式必须长期并存。Web 化不能以破坏 OpenRice 本地优先能力、上游兼容标识或桌面端可用性为代价。

## 二、设计原则

1. **默认拒绝：** 未被明确授权的访问一律拒绝。
2. **服务端裁决：** 前端显隐只改善体验，不能成为权限边界。
3. **租户优先：** 所有查询、搜索、缓存、文件和任务都必须带组织与工作区范围。
4. **资源有主：** 所有业务资源必须有创建者、归属空间和可见范围。
5. **凭证隔离：** OAuth、API Key 和企业账号按用户或组织独立绑定，禁止明文共享。
6. **最小权限：** 新成员、新技能和新数字员工默认只有完成任务所需的最低权限。
7. **高风险留痕：** 管理、外部写入、发布、删除、导出和权限变更必须审计。
8. **双模式兼容：** 桌面端继续支持本地单用户；Web 端使用正式多租户模型。
9. **统一授权模型：** SkillHub、数字员工、任务、Memory 和连接器不各自发明角色系统。
10. **先基础隔离，再复杂协作：** P0 先保证身份、归属和隔离正确，再增加审批、共享和企业能力。

## 三、目标架构

```text
Desktop Client                         Web Client
     │                                     │
     ├── Local Mode                        ├── Auth Session
     │   ├── Local DB                      ├── Organization / Workspace
     │   ├── Keychain                      └── Server-side Authorization
     │   └── Local Runtime                          │
     │                                              ▼
     └──────────── Shared Domain Contracts ── API / Policy Layer
                                                    │
                         ┌──────────────────────────┼─────────────────────────┐
                         ▼                          ▼                         ▼
                  Tenant-aware DB             Secret Vault             Object Storage
                         │                          │                         │
                         └────────────── Worker / Queue / Scheduler ─────────┘
                                                    │
                                          Audit / Metrics / Alerts
```

共享的是领域契约、权限语义和业务能力，不要求桌面端与 Web 端使用相同的存储和凭证实现。

## 四、核心领域模型

### 4.1 User

表示自然人账号，不直接承载组织角色。建议包含：

- 稳定用户 ID；
- 登录标识、显示名称和头像；
- 账号状态与安全状态；
- 最近登录和会话信息；
- 个人偏好与默认工作区。

### 4.2 Organization

企业或独立团队的顶级安全边界。组织间数据必须物理或逻辑严格隔离。

### 4.3 Workspace

组织内的协作空间，用于承载项目、团队或部门级资源。一个组织可以有多个工作区。

### 4.4 Membership

连接 User 与 Organization/Workspace，记录成员状态、角色、加入方式和有效期。禁止直接把角色字段写在 User 上。

### 4.5 Role / Permission

角色是一组权限的集合；权限是针对资源和动作的稳定标识。建议使用：

```text
resource.action

workspace.manage
member.invite
skill.install
employee.run
memory.read
connector.authorize
audit.read
```

### 4.6 ResourceOwnership

所有核心资源至少需要以下归属信息：

```text
owner_id
organization_id
workspace_id
visibility
created_at
updated_at
```

可见范围统一为：

- `personal`：仅创建者和明确授权者可访问；
- `workspace`：工作区成员根据角色访问；
- `organization`：组织成员根据组织策略访问。

不建议在 P0 开放匿名公开资源。

### 4.7 CredentialBinding

记录连接器凭证属于哪个用户、工作区或组织，只保存 Secret Vault 引用和授权元数据，不在普通业务表中存储明文凭证。

### 4.8 Session / Invite / AuditLog

- Session 管理登录设备、过期、撤销和异常登录；
- Invite 管理邀请人、目标组织、预设角色和有效期；
- AuditLog 记录主体、动作、资源、结果、时间、来源和必要的变更摘要。

## 五、基础角色

| 角色             | 定位       | 默认能力                                 |
| ---------------- | ---------- | ---------------------------------------- |
| `platform_admin` | 平台管理员 | 平台配置、组织治理、安全与全局审计       |
| `org_admin`      | 组织管理员 | 成员、工作区、组织资源和组织连接器管理   |
| `builder`        | 建设者     | 创建技能、数字员工、自动化任务和共享资源 |
| `member`         | 成员       | 使用被授权的技能、数字员工、任务和资料   |
| `viewer`         | 访客       | 只读访问明确共享的内容                   |

P0 使用固定角色，避免过早建设复杂的自定义权限编辑器。P2 再增加自定义角色，但底层权限标识从第一天保持稳定。

## 六、权限矩阵

`管理` 表示可创建、编辑、删除和授权；`使用` 表示可运行但不可更改治理配置；`只读` 表示只能查看。

| 资源            | platform_admin | org_admin  | builder            | member             | viewer       |
| --------------- | -------------- | ---------- | ------------------ | ------------------ | ------------ |
| 组织与安全策略  | 管理           | 组织内管理 | 无                 | 无                 | 无           |
| 成员与角色      | 管理           | 管理       | 只读               | 无                 | 无           |
| 工作区          | 管理           | 管理       | 创建/编辑授权空间  | 使用               | 只读         |
| SkillHub        | 管理           | 组织内管理 | 创建/发布申请/安装 | 安装与使用授权技能 | 只读         |
| 数字员工        | 管理           | 组织内管理 | 创建/配置/运行     | 运行授权员工       | 查看授权结果 |
| 任务与 Loop     | 管理           | 组织内管理 | 创建/运行          | 运行授权任务       | 查看授权结果 |
| Memory / 资源库 | 管理           | 组织内管理 | 上传/编辑授权空间  | 读写授权空间       | 只读         |
| 连接器          | 管理           | 组织级管理 | 绑定自己的账号     | 使用授权连接器     | 无           |
| 审计日志        | 全局查看       | 组织内查看 | 查看自己的运行     | 查看自己的运行     | 无           |

实际权限必须同时满足：

```text
角色权限
AND 资源归属范围
AND 资源状态
AND 组织安全策略
AND Skill / 数字员工声明权限
```

## 七、模块接入要求

### 7.1 对话与会话

- 会话默认归个人，可显式共享到工作区；
- 附件、工具调用和产物继承会话范围，但可以被进一步收紧；
- 分享链接不得绕过成员身份和资源授权。

### 7.2 任务与 Loop

- 定时任务必须有执行主体、目标工作区和凭证绑定；
- 成员被移除或权限降低后，相关任务需要暂停或重新授权；
- Worker 执行时重新校验权限，不能沿用创建时的永久授权。

### 7.3 SkillHub

- Skill 可安装到个人空间或工作区；
- 企业专属 Skill 不能被其他组织发现或下载；
- 安装不等于获得连接器、文件或外部写入权限；
- Skill 版本更新不能扩大权限而不触发重新确认。

### 7.4 数字员工

- 数字员工属于个人或工作区；
- 实际权限是用户权限、员工权限、Skill 权限和数据范围的交集；
- 数字员工不能借服务账号读取操作者无权访问的数据；
- 每次运行记录操作者、模型、Skill、工具、来源、审批和产物。

### 7.5 Memory 与资源库

- 检索、向量查询和摘要生成必须带组织/工作区过滤；
- 禁止先跨租户召回再在应用层过滤；
- 共享 Memory 与用户私有 Memory 分开存储和授权；
- 删除成员或资源后，应同步处理索引、缓存和派生产物。

### 7.6 连接器与凭证

- 用户级连接器只代表该用户执行；
- 组织级连接器由管理员授权，并限制可使用的工作区、技能和数字员工；
- 前端永远不返回完整 Secret；
- 日志、错误和审计信息必须脱敏。

## 八、桌面与 Web 双模式

### 桌面本地模式

- 可继续使用本地数据库、本地文件、Keychain 和本地运行时；
- 单用户模式不强制创建云端组织；
- 本地资源使用稳定的本地所有者标识；
- 未来同步到 Web 时通过显式迁移流程补齐组织和工作区归属。

### Web 团队模式

- 使用正式身份服务和服务端会话；
- 数据库、对象存储、缓存、任务和向量索引全部租户感知；
- 凭证进入加密 Secret Vault；
- Loop、定时任务和数字员工运行进入服务端队列与 Worker；
- 所有外部调用记录实际操作者、授权来源和作用范围。

### 兼容约束

- 不重命名上游同步依赖的内部标识；
- OpenRice 品牌覆盖继续集中管理；
- 权限领域层尽量与存储实现解耦；
- 上游更新通过独立同步分支进入，再由 Codex 检查冲突和合并。

## 九、认证与会话

P0 至少支持：

- 邮箱或受控账号登录；
- 密码安全存储或外部身份提供商；
- 会话过期、退出和设备撤销；
- 找回与邀请流程；
- 管理员禁用账号；
- 登录、邀请和权限变更审计。

生产环境禁止使用演示账号、共享管理员密码或仅前端保存的角色信息。

P3 再扩展 OIDC、SAML、LDAP 和 SCIM。身份协议和组织模型要提前解耦，避免未来重写全部权限逻辑。

## 十、API 授权流程

每个受保护请求建议经过统一中间件：

```text
验证 Session
  → 解析 User
  → 确认 Organization / Workspace Membership
  → 计算 Role Permissions
  → 加载资源归属
  → 应用组织策略和资源状态
  → 允许或拒绝
  → 高风险动作写入 AuditLog
```

数据查询必须从租户范围开始构造，不能先查出全部数据再做内存过滤。

## 十一、安全与测试

### 必测场景

- 跨组织读取、修改、删除和搜索；
- 猜测文件 URL、任务 ID、会话 ID 和资源 ID；
- 普通成员调用管理员 API；
- 角色降级后继续使用旧会话或旧任务；
- Skill 或数字员工尝试扩大声明权限；
- 缓存、向量索引、日志和导出中的跨租户泄漏；
- OAuth 回调绑定到错误用户或组织；
- 被移除成员的定时任务和连接器继续运行。

### 测试层级

- 权限策略单元测试；
- API 越权与跨租户集成测试；
- 数据迁移和回滚测试；
- Web 关键路径端到端测试；
- 桌面本地模式回归测试；
- 审计完整性和敏感字段脱敏测试。

## 十二、分期路线

### P0：身份与隔离基础

1. User、Organization、Workspace、Membership 数据模型；
2. 注册、登录、退出、邀请和会话管理；
3. 固定角色与统一授权中间件；
4. 核心资源归属字段；
5. 数据查询、文件和 RAG 的租户隔离；
6. 基础审计与管理员入口；
7. 越权、跨租户和角色降级测试。

### P1：团队可用

1. SkillHub 个人/工作区安装；
2. 连接器和 Secret 的用户/组织绑定；
3. Memory、资源库和文件共享范围；
4. 成员、角色和工作区管理 UI；
5. 权限拒绝、空状态和重新授权体验。

### P2：协作生产

1. 数字员工共享、分配和运行权限；
2. 团队任务、审批、通知和运行历史；
3. 工作区模板、统计和配额；
4. 自定义角色与更细粒度权限。

### P3：企业能力

1. OIDC / SAML SSO；
2. LDAP / SCIM；
3. 完整审计、留存、导出和风控策略；
4. 私有化部署和组织策略中心。

## 十三、P0 验收标准

- 两个不同组织的用户无法通过 UI、API、搜索、文件 URL、缓存或任务记录访问对方数据；
- 所有受保护 API 均在服务端校验身份、成员关系、权限和资源归属；
- 管理员可邀请、分配角色、禁用和移除成员；
- 普通成员不能访问管理页面或执行管理 API；
- Skill、数字员工、Memory、资源库、文件、任务和连接器均有明确归属；
- Web 凭证不进入仓库、浏览器日志或普通业务表明文字段；
- 桌面本地模式继续正常工作；
- 自动化测试覆盖跨租户、越权访问、角色降级和凭证隔离。

## 十四、协作方式

1. MET-33 先完成总体架构、权限矩阵、数据迁移和 API 清单评审；
2. 评审通过后拆分 P0 子 Issue，按领域边界并行开发；
3. M5 与 lindong 承接独立任务并提交 PR，不负责合并；
4. Codex 负责跨模块 Review、冲突处理、迁移顺序、测试审计和合并到 `main`；
5. 涉及身份、数据隔离、Secret、OAuth、RAG 和文件访问的改动必须有安全测试；
6. 不在用户系统开发中夹带无关品牌重构或上游标识修改。
